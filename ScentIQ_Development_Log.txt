4. ARCHITECTURE
--------------------------------------------------------------------------------
High-level:

  Browser / Android PWA
    |-- Supabase JS (anon key + RLS): auth, catalogue reads, search, feedback,
    |   reviews, collections, similar perfumes via pgvector RPC
    |-- FastAPI: POST /v1/recommend, /v1/explain, /v1/model/info
    |
  Supabase Postgres (system of record)
    |-- perfumes, perfume_vectors, clusters, reviews, profiles,
        user_preferences, feedback, collections, collection_items
    |
  FastAPI (stateless ML service)
    |-- loads model artifacts at startup
    |-- receives profile inputs (IDs, notes, filters), returns ranking + reasons
    |-- no user PII required
    |
  GitHub Actions
    |-- CI on PR, migrations on merge, keepalive cron, manual retrain

Key reliability decision:
  Catalogue, detail pages, search, reviews, and similar perfumes work directly
  from Supabase and do NOT depend on the ML API. If Render is cold, the site is
  still fully usable; only the Discover ranking shows a "warming engine" state.

Data flow - recommendation:
  User profile (loved IDs + notes + filters)
    -> FastAPI builds user vector / cluster affinity
    -> candidate filtering (budget, season, occasion, gender, exclude rated)
    -> hybrid score: content similarity + tree probability + cluster affinity
       + quality prior
    -> MMR diversity rerank
    -> top N with explanation text and confidence

Data flow - feedback and learning:
  Like/dislike/review in UI
    -> Supabase (RLS-protected)
    -> profile affinity updates immediately in the client
    -> manual/periodic retrain workflow pulls feedback, retrains tree,
       validates metrics, commits artifacts, redeploys API
  This is the honest ML loop: simulated labels for cold start, real labels over
  time.

5. DATA STRATEGY
--------------------------------------------------------------------------------
PRIMARY DATASET: Scento Perfume Database (Hugging Face)
  URL     : https://huggingface.co/datasets/scento/perfume-database
  License : CC BY 4.0 - attribution required in the app and README
  Size    : 1,479 perfumes, 160 houses, 420 raw materials
  Fields  : id, name, house, year, perfumers, concentration, family,
            secondary_family, character, seasons, times_of_day, top_notes,
            heart_notes, base_notes, notes (flat), description,
            popularity_rank, url
  Gaps    : no prices, no community ratings, no longevity/sillage, no images
  Why     : clean, licensed, and it has the season/time metadata the brief needs

OPTIONAL SECONDARY: Kaggle Fragrantica datasets
  https://www.kaggle.com/datasets/ledecanteur/fragrantica-perfumes
  https://www.kaggle.com/datasets/olgagmiufana1/fragrantica-com-fragrance-dataset
  Use for scale/community ratings only if time allows. Scraped provenance and
  license must be checked. Do not redistribute raw data publicly.
  Decision for v1: Scento only. Cleaner, safer, faster, and 1,479 perfumes is
  plenty for K-Means, a tree, and a polished product.

PRICE TIER (estimated, never pretend it is exact)
  Tier 1 "Accessible"  : Arabian houses, drugstore/designer diffusion
  Tier 2 "Designer"    : mainstream designer brands
  Tier 3 "Premium"     : premium designer / entry niche
  Tier 4 "Luxury"      : niche, heritage, high-end houses
  Build brand_price_tier.csv for the top ~120 houses, fall back to house type.
  UI label: "Estimated retail tier" with tooltip explaining the estimate.

RATINGS / LONGEVITY / SILLAGE
  Do not fabricate. Start empty and collect real community votes:
    reviews(rating 1-5, longevity 1-5, sillage 1-5, text)
    perfume_stats view aggregates count + average.
  Until then show "New - be the first to rate" or popularity rank.
  If Kaggle ratings are merged later, label the source and date.

IMAGES / VISUALS
  No scraped brand photos. Generate 10-14 abstract "scent family" visuals with
  ImageGen (citrus, floral, oud, gourmand, aquatic, woody, musk, spicy, green,
  fruity, amber, leather). Map each perfume to a family visual + deterministic
  CSS gradient derived from its ID, so every card looks unique without 1,479
  image assets.

CLEANING RULES
  - Scento CSVs are pipe-delimited; list fields use semicolons.
  - Lowercase notes, trim, map aliases and synonyms, merge singular/plural.
  - Drop notes appearing in fewer than 5 perfumes from the model features,
    keep them in display data.
  - Deduplicate by normalized (name, house, year).
  - Parse seasons/times_of_day into arrays; validate allowed values.
  - Handle missing year/concentration with "Unknown" + missing indicator.
  - Use a schema validator (pandera or custom) and fail loudly.
  - Keep raw data immutable in data/raw; write data/processed as parquet.
  - Attribution block in About page and README.

DATA MODEL (Supabase)
  profiles(id uuid PK -> auth.users, display_name, avatar_url, onboarded,
           created_at)
  user_preferences(user_id PK, loved_perfume_ids text[], love_notes text[],
           avoid_notes text[], budget_tier int, seasons text[], occasions
           text[], gender text, updated_at)
  perfumes(id text PK, name, house, year, concentration, family,
           secondary_family, character, gender, seasons text[],
           times_of_day text[], top_notes text[], heart_notes text[],
           base_notes text[], notes text[], description, popularity_rank,
           price_tier int, image_key text, vector vector(48), cluster_id int)
  clusters(id int PK, name, description, top_notes text[], color, centroid
           vector(48), size int)
  feedback(id uuid PK, user_id, perfume_id, action text check in
           ('like','dislike','neutral'), created_at, unique(user_id, perfume_id))
  collections(id uuid PK, user_id, name, is_public bool, created_at)
  collection_items(collection_id, perfume_id, added_at, PK(collection_id,
           perfume_id))
  reviews(id uuid PK, user_id, perfume_id, rating int 1-5, longevity int,
           sillage int, body text, created_at, unique(user_id, perfume_id))
  Indexes: perfume name trigram, GIN on notes/seasons, ivfflat on vector,
           feedback(user_id), reviews(perfume_id).
  RLS: public read on perfumes/clusters/reviews (limited profile fields);
       users write only their own rows (auth.uid() = user_id).

6. MACHINE LEARNING DESIGN
--------------------------------------------------------------------------------
6.1 PERFUME FEATURES
  - Note families: citrus, floral, woody, amber/oriental, gourmand, spicy,
    aromatic, musky, fruity, green, aquatic, leather, animalic, powdery.
  - Top ~120 individual notes (frequency >= 5), multi-hot.
  - Accords/families: family + secondary_family one-hot; derived accord strength
    from note-family counts.
  - Context: season multi-hot, time-of-day multi-hot, gender, concentration,
    decade, price tier.
  - Quality: popularity rank (normalized); Bayesian community rating later.
  Pipeline: TF-IDF on note-family/accord tokens -> TruncatedSVD (30-50 comps)
  -> L2 normalize. Context/quality features are scaled separately and appended
  for the tree, not forced into the clustering vector.
  Never cluster directly on 2,600 sparse raw notes.

6.2 K-MEANS
  - Try k = 6..14. Score with silhouette (sample), Davies-Bouldin, and human
    inspection of top notes/accords per cluster.
  - Fixed random_state=42, n_init=20. Save centroids and labels.
  - Name clusters from over-represented notes ("Oud, Amber & Spice",
    "Fresh Citrus & Aquatic", "Vanilla & Gourmand", etc.).
  - Write a cluster description for the UI; never show "Cluster 7".
  - 2-D map via PCA (deterministic) for the profile page; optionally UMAP
    offline if it improves separation, but do not add a heavy runtime dependency.

6.3 DECISION TREE - THE CRITICAL PART
  There are no individual user ratings in public datasets. Training "will this
  user like it?" requires labels. Two-stage solution:

  Stage A - cold start with simulated users
    - Define 8-12 latent archetypes with hidden preference vectors over note
      families/accords and context preferences.
    - Generate 200-400 users per archetype with noise and varied filters.
    - For each user, sample 100-200 candidate perfumes, compute hidden affinity,
      label top ~30% as liked. Keep realistic imbalance (~65/35 or 70/30).
    - Observable pair features ONLY:
        note_overlap, avoid_note_conflict, family_match, cluster_affinity,
        price_fit, season_match, occasion_match, gender_match,
        popularity_prior, concentration_match, community_rating (when real)
    - Train DecisionTreeClassifier(max_depth 5-6, min_samples_leaf 30-50,
      class_weight='balanced', random_state=42).
    - Split by USER with GroupShuffleSplit, never by row.
    - LEAKAGE GUARDRAIL: labels must come from the hidden user vector, not from
      the observable features. Add a test that proves users do not overlap
      between train and test. If accuracy is ~99%, assume leakage and audit.
    - Export tree_rules.json for explanations and a later TypeScript fallback.

  Stage B - real feedback
    - Persist every like/dislike/review.
    - Update the user vector immediately: v_user += alpha * v_perfume for likes,
      v_user -= beta * v_perfume for dislikes (alpha ~0.2, beta ~0.15), normalize.
    - Recompute cluster affinity from the user's liked perfumes.
    - Manual/periodic retrain once >= 200-500 real interactions exist. Compare
      simulated vs real metrics and report both.
    - Active learning idea (stretch): surface items with tree probability near
      0.5 to collect the most informative feedback.

6.4 HYBRID RANKING
  score = 0.40 * content_cosine
        + 0.30 * tree_probability
        + 0.20 * cluster_affinity
        + 0.10 * quality_prior
  Hard filters first: budget tier, seasons, occasion, gender, exclude already
  rated/liked perfumes (unless "show more like this").
  Then MMR diversity rerank (lambda ~0.7) so the list is not ten oud scents.
  Unknown user: content-only + popularity, labeled "Starter picks".

6.5 EXPLANATIONS
  Generate from tree path + feature contributions, deterministic templates:
    "You lean woody-amber. This sits in Oud, Amber & Spice, shares 4 of your 6
     favourite notes (oud, amber, saffron, cedar), fits winter/evening, and is
     within your Designer tier."
  Always show conflicts:
    "Heads up: it contains rose, which you asked to avoid."
  Show a confidence band, not a fake precise percentage. No LLM needed; the
  deterministic explanation is defensible and cannot hallucinate notes.

6.6 EVALUATION
  Clustering : silhouette, Davies-Bouldin, cluster top-note sanity, size balance.
  Tree       : balanced accuracy, precision/recall/F1, ROC-AUC, per-user
               precision@10, confusion matrix; report simulation caveat.
  Ranking    : hit rate@10 on held-out liked perfumes, intra-list diversity,
               catalogue coverage, novelty.
  Real test  : 5-10 people x 20 ratings; compare predicted vs actual; report
               honestly. This is the strongest evidence in the viva.
  Targets (not guarantees): silhouette > 0.10, balanced accuracy > 0.75,
  simulated hit@10 > 0.60, warm recommendation p95 < 300 ms.

6.7 MODEL CARD / LIMITATIONS
  Document data source and date, feature definitions, simulated-label method,
  known biases (popularity, Western/designer skew, missing prices), evaluation
  caveats, privacy (no PII sent to the ML API), and intended use (discovery,
  not medical/allergy advice). Allergy warning in the UI: notes are descriptive,
  not a safety guarantee.

  export feedback from Supabase -> retrain -> evaluate -> upload artifacts ->
  commit small artifacts -> redeploy API. Fails if metrics regress beyond a
  threshold; never auto-deploy a worse model.

Deploy:
  Vercel and Render watch main and auto-deploy after CI.
  Preview URL on every PR (Vercel).
  Rollback: Vercel instant rollback; Render previous deploy; migrations are
  forward-only with a documented manual rollback.

Branching:
  main protected; feature branches; conventional commits; PR template with
